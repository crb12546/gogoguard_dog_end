# Livox 实时帧修复与冷启动验证（2026-07-25）

## 结论

本轮已经把约 `1.7 s` 的稳定延迟定位到 Livox 驱动内部 FIFO，并完成修复。

核心不是 15W/25W，也不是 FAST-LIO 只使用了一个 CPU 核，而是：

1. MID-360S 每 `99.36 ms` 产生一帧；
2. Livox 自定义消息的复制、序列化和发布在启动阶段平均需要
   `114–161 ms/帧`，稳定阶段本轮仍约 `102–106 ms/帧`；
3. 生产速度高于消费速度时，原驱动继续按 FIFO 发布旧帧；
4. 请求长度 10 的环形队列实际向上取整为 16，满后又保留旧帧、
   丢弃新帧，因此延迟稳定在约 16 帧而不会继续增加。

分段测量直接观测到驱动出口：

- `343 ms / 队列深度 4`
- `656 ms / 深度 8`
- `1.00 s / 深度 11`
- `1.68 s / 深度 16`
- `1.96 s / 深度 16`

同期 FAST-LIO 输入约 `1.98 s`，与驱动出口约 `1.96 s` 对齐，
说明 DDS 和 FAST-LIO 只增加了几十毫秒；秒级延迟在进入
FAST-LIO 前已经形成。

原始分段证据见
[`run03_publish_stage_probe/livox.log`](run03_publish_stage_probe/livox.log)
和
[`run03_publish_stage_probe/fast_lio.log`](run03_publish_stage_probe/fast_lio.log)。

## 实施内容

1. Sampling 状态之前的帧不再进入不可消费的发布队列；10 次正式
   冷启动每次都明确丢弃了 20 个配置完成前的帧。
2. 点云发布线程不再固定休眠 3 秒，直接通过信号量等待第一帧
   Sampling 数据。
3. 发布端每次处理队列中最新的**完整帧**，跳过已经落后的完整帧。
   不会截断一帧内部的点，也不会拼接不同帧。
4. 新增逐帧新鲜度门槛：
   - 连续 10 个唯一 FAST-LIO 输出；
   - 每帧墙钟年龄 `<= 250 ms`；
   - 这 10 帧内部的 9 个时间间隔均在 `50–150 ms`；
   - 任一条件失败就重置计数，120 秒仍不满足则底座失败退出。
5. 门槛同时接入 `base_bringup.sh` 和 SaaS 实际调用的
   `ensure_base_ready.sh`，不再通过“一秒一次的统计日志存在”来
   假定定位是新鲜的。
6. 保留每秒一次的 Livox 出口统计，记录出口年龄、发布耗时、
   队列深度和跳过帧数，便于后续现场审计。

## 证伪过程

- 只做“Sampling 前不入队”时，首轮仍从 `2.214 s` 开始，
  约 40 秒后才追到 250 ms 内。这证明该改动只解决了一部分启动积帧。
- 再去掉固定 3 秒休眠后，延迟仍稳定在 `1.67–1.78 s`，
  严格门槛在 120 秒后正确拒绝启动。这证明休眠也不是唯一主因。
- 加入驱动出口测量后，队列深度与出口年龄同步增长到
  `16 / 1.96 s`，且 FAST-LIO 输入年龄与之对齐，才最终证明主因。
- 改为“最新完整帧优先”后，队列峰值降到 1–3，秒级积压消失。
