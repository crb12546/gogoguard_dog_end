# 第一部分 · 总的

## 这个系统在干什么

一句话:**让狗自己走一条人工录好的固定路线,过程中把数据传回平台。**

拆开就是三件事:
1. **先有人带着狗走一遍**,把路线记成文件
2. **狗自己按这个文件走**,边走边知道自己在哪、该往哪转
3. **全程记录**,你在电脑上分析走得准不准

## 整体状态

**能跑,而且跑得准。** 最后一次巡检(7/26)跟线误差 3 厘米。
删掉用不上的代码之后,**在真狗上编译 9/9 通过,自检 0 断裂**。

**问题不在"能不能跑",在"改不改得动"。**

## 总的问题,四条

### 一、真正干活的代码很少,但埋得很深

```
让狗动的核心算法        331 行   ← 四步逻辑,就这么点
包着它的外壳          1,259 行   ← 是算法的 3.8 倍
记录和观测            5,370 行   ← 比整条运动链(3,125)还大 72%
一个文件干六件事      3,633 行   ← 其中单个函数就 1,250 行
```

**不是这些代码没用** —— 观测你要用来分析、外壳的门禁是必须的。
**是位置不对**:算法被裹在外壳里、观测长在决策逻辑里、六件不相干的事挤在一个文件里。

### 二、进程之间靠"约好的字符串"通信,没有任何校验

这个系统的十几个进程**不通过函数调用**,全靠约定:

| 类型 | 数量 | 改错一个字母会怎样 |
|---|---:|---|
| 门文件(靠文件存在传信号) | 7 | 狗永远不动,**不报错** |
| 日志字符串当就绪信号 | 5 | 启动永远卡住,**不报错** |
| 退出码 | 11 | 错误被当成别的错误 |
| 环境变量 | 174 | 默默用了默认值 |
| ROS 话题名 | 5 | 指令发不到,**不报错** |
| 共享文件 | 1 生产者 / 5 消费者 | 5 个地方同时瞎 |

**这是改造最大的风险源。** 也是为什么第一件事必须是建验证网,不是搬代码。

### 三、没有测试 → 不敢改 → 只能往上堆

这才是根因,不是能力问题:

```
系统要"能跑起来"
   ↓
每来一个新需求 → 在最方便的地方加一段(通常是那个 3633 行的文件)
   ↓
没有测试 → 不敢动已有代码 → 只能继续加
   ↓
1250 行的函数 · 174 个环境变量 · 算了不用的参数
```

### 四、有些设计问题,不是重构能解决的

最典型的一条:**狗摆歪 1 度,整条链路没有任何环节能发现**
(路线会被转过来迁就狗,所有检查都只可能通过,436 米下来偏 7.61 米)。

**这类问题写进来是让你知道它存在,但本轮不动它** —— 它需要新设计,属于第 2 步。

## 总的打算

**这一轮只做一件事:把代码搬回它该在的位置。行为一个字节不变。**

```
第 0 步  建验证网          不动任何生产代码。零风险
第 1 步  拆那个 1250 行的函数
第 2 步  拆那个干六件事的文件
第 3 步  控制层归位(算法和外壳合到一处,门禁与记录拆开)
第 4 步  观测层剥离
第 5 步  目录归位(建图挪出巡检运行时)
第 6 步  真机跑一次巡检验证
```

**44 个活代码文件里,42 个是整个搬走、一个字不改。**
真正要动内容的只有 2 个文件:那个 3633 行的和那个 1259 行的。

## 你怎么判断我做得对不对

不用读代码,盯三个数:

| 问题 | 我要能回答 |
|---|---|
| 搬走的 42 个文件,内容真没动? | `diff` 输出为空 |
| 57 条启动命令真没变? | 规范化后逐字节相同 |
| 狗的决策真没变? | 6833 条历史记录回放,逐位相同 |

**任何一条答不上来,就是我改坏了。**

## 本轮明确不做

| 不做 | 为什么 |
|---|---|
| 不改算法逻辑、不改参数值 | 违反"结果一样"这条底线 |
| 不改门文件名 / 日志文案 / 退出码 / 话题名 | 最危险的一类,要改也得等验证网建好后单独一轮 |
| 不修"云端参数调了没用" | 那是改行为。本轮只暴露、只记录 |
| 不合并进程 | 现在看不出该合并谁跟谁;归位后一眼能看出,那时是小事 |
| 不做避障 | 第 2 步的新需求,在本轮之后 |
| 不碰任何 🎯 设计问题 | 同上 |

## ⓪ 开机常驻

**现在有什么**
四个程序开机自动跑起来,一直跑到关机:命令循环、视频循环、补传循环、有线 SSH 救援。

**它们在影响什么**
命令循环是整个系统的入口 —— **每 5 秒问云端一次"有活吗"**,你在平台上点"开始巡检"就是被它接到的。

**通过什么方式**
狗背 4G,**没有固定公网 IP,平台连不进来**。所以只能狗主动 POST 到 `/robot/heartbeat`:
请求体带状态上去,响应体带命令下来。一个接口两个方向。

**为什么这么设计**
因为巡检可能失败。如果巡检是常驻服务,它崩了整个狗就失联。
现在是:**通信和救援常驻,干活的临时拉起**。干活那摊崩了,你还能看到狗、还能 SSH 上去。

**当前怎么做的**
四个 `systemd` 服务(已在真机核实 enabled + running)。
巡检不在这四个里 —— 它是命令循环收到指令后**临时**拉起的第五摊东西,跑完就拆。
雷达和 FAST-LIO **也不是开机自启**,同样是按需拉起。

**问题**

🔧 **结构**:拉起这四个循环的代码,和它们各自要干的事,全在同一个 3633 行文件里。
"跟云端说话"和"编排巡检启动"是两件完全不同的事,却互相看得见对方的所有内部变量。

**本轮改成什么**
把"跟云端说话"拆到 `cloud/`,把"编排巡检"拆到 `orchestration/`。
四个服务的启动方式、轮询间隔、接口路径**一个字不改**。

## ① 录制路线

**现在有什么**
一个程序,人拿手柄遛狗时在后台跑,把狗走过的位置记成 CSV。

**它在影响什么**
**它的产物就是巡检的"数据"** —— 没有它,巡检无路可走。

**通过什么方式**
订阅狗的位置,**每往前走 0.4 米记一行**:`id, x, y, yaw, v`。
436 米的路线大约 1100 行(实测那次是 1277 个点)。

**为什么是 0.4 米**
太密(比如 0.05 米)→ 文件巨大,而且记录噪声被完整保留,路线变抖;
太疏(比如 2 米)→ 拐弯的形状丢了,狗会切角。
**这个数没有理论依据,是调出来的。**

**当前怎么做的**
`route_recorder.py`(132 行)+ 一个证据链黑盒 `route_recording_blackbox.py`(1760 行)。
录制和巡检**互斥**,靠一个空文件 `.route_recording_enabled` 挡着。

**问题**

🔧 **结构**:录制的 1892 行和巡检运行时混在同一个 `src/` 下。
它们是互斥的两件事,却打包在一起,每次编译都编。

🎯 **设计(本轮不改)**:CSV 里记的速度 `v` **是假的** ——
它不是狗当时实际多快,是一个写死的常数 `0.20`,每一行都一样。
所以跟线器**根本不读这个字段**。这是一列没有意义的数据。

**本轮改成什么**
整个搬到 `recording/`,和巡检运行时分开。**内容一个字不改。**
那列假的 `v` 本轮不动 —— 删它要同时改录制端和读取端,是改行为。

## ② 感知:雷达和 FAST-LIO

**现在有什么**
一台 Livox MID-360 激光雷达,和一套叫 FAST-LIO 的 SLAM 程序。

**它在影响什么**
**它是全系统唯一的位置来源。** 后面所有环节 —— 路线对齐、跟线、安全层、观测 —— 吃的都是它的输出。

**通过什么方式**
雷达每秒往四周打十万个激光点。FAST-LIO 把这一帧的形状和上一帧对齐,
算出"这 0.1 秒我挪了多少、转了多少",一路累加得出位置。

**为什么用它**
室内 GPS 不行(没信号,精度 3-5 米,巡检要厘米级);
四足狗没有轮子,轮式里程计也用不了。

**当前怎么做的**
`base_bringup.sh` 在收到巡检命令后拉起两个进程:雷达驱动 + FAST-LIO。
配两个探针查"雷达有没有出数""位置是不是新的"。

**问题**

🔧 **结构**:起停脚本和探针散在 `scripts/` 里,和其他十几个脚本混着。

⚠️ **实测发现(2026-08-01,不是结构也不是设计,是性能)**:
```
livox_ros_driver2_node   1.128 核    ← 雷达驱动
fastlio_mapping          0.210 核    ← SLAM 算法本体
```
**驱动吃的 CPU 是算法本体的 5.4 倍。** 一个"把网络包解成点云再发出去"的程序,
比整套 IESKF + ikd-Tree 还贵 5 倍。这是稳态第一大开销,而且它的配置在我们手里。

🎯 **设计(本轮不改)**:**只有这一个位置来源,没有第二个做交叉验证。**
FAST-LIO 要是算错了,没有任何东西能发现。狗会坚信自己在一个错误的地方。

**本轮改成什么**
5 个文件搬到 `runtime/perception/`,内容不改。
雷达驱动那 1.128 核**本轮只记录、不优化** —— 优化它要改配置,是改行为。

## ③ 扶正:那两个 IMU

**现在有什么**
狗身上有两个 IMU(测姿态和重力的传感器):**一个在雷达里面**(跟雷达一起歪装了 34 度),
**一个在狗身上**(正的)。

**它们各自在影响什么**
- **雷达那个**:数据直接进 FAST-LIO,参与推算狗的位置和姿态 —— **它是定位的输入之一**
- **狗身那个**:不进定位,**只在启动的时候用一次**

**通过什么方式影响**
两个各自测一次重力方向 → **互相对答案** → 差超过 3 度就丢弃这次测量 →
攒够 15 次一致的 → 算出一个"扶正旋转" → **当场冻结,整趟不再变**。

这个旋转会作用在三个地方:**狗的位置、狗的朝向、整条路线的坐标**。

**为什么需要这么做**
雷达是斜着装的,往下歪 34 度(实测 34.324°)。**FAST-LIO 不知道这件事**,
它默认"雷达的正上方就是世界的正上方"。

于是它算出来的整个世界是歪的。打个比方:

> 你戴着一副歪 34 度的眼镜看房间,会觉得地板和墙都是斜的。
> 你在这个视角下画的地图**自己是自洽的**,按图走也能走通。
> **但高度全错了** —— 真实平地上走 10 米,你的地图上会显示"同时上升了 5.6 米"。

对巡检的实际影响:记路线和走路线**只要在同一个歪系里,居然能走通**。
但只要中间坐标系变了一次(比如定位重启),两边就对不上,狗会走飞。

**那为什么需要第二个 IMU?**
因为雷达自己的 IMU 和雷达装在一起,**雷达歪它也歪**,它报的"重力方向"当然也是歪的。
**所以必须有一个正装的 IMU 做对照。** 这就是狗身那个 IMU 存在的全部理由。

**当前是怎么做的**
代码在 `waypoint_follower_go2_2_trace.py` 里 —— **就是那个 1259 行的跟线器外壳**:
```
:214  攒够 15 个一致样本才锁
:223  两个 IMU 差超过 3 度就丢弃
:546  雷达 IMU 的数据入口
:515  狗身 IMU 的数据入口
```

**问题**

🔧 **结构 ★ 这是本轮最该改的一处**:
**扶正是"定位"的事,代码却写在"控制器"里面。**

后果很具体:想单独验证扶正算得对不对,**必须启动整个跟线器**;
反过来,想测跟线算法,又得先把两个 IMU 的数据喂进去。**两件事拆不开。**

🎯 **设计(本轮不改)**:**冻结之后没有第二次机会。**
如果启动那一刻测错了(狗停在斜坡上、或者正好有人碰它),整趟都错,
而且链路上**没有任何环节能发现**。

**本轮改成什么**
把扶正逻辑从跟线器外壳里**搬出来**,放进 `runtime/localization/`。

搬完之后的样子:**给它两个 IMU 的读数,它给你一个旋转矩阵** —— 输入输出清晰,可以单独测。

**⚠️ 一行逻辑都不改**:15 个样本、3 度门限、冻结策略,全部原样。只是换位置。
"冻结没有第二次机会"那个设计问题,留给第 2 步。

## ④ 路线对齐

**现在有什么**
一个程序,在巡检启动时把整条路线**平移+旋转**,让路线的起点正好落在狗现在的位置上。

**它在影响什么**
**它决定了狗认为"路线在哪"。** 之后跟线器读的是它的产物。

**通过什么方式**
录路线时狗站在 A 点朝北,今天你把狗放在 A 点附近 —— 不可能完全一样。
两个思路:把狗挪准(做不到,人手放不准),或者**把路线整体挪过来迁就狗**。
现在用的是后者。

**为什么这么做**
因为人手放不准。这个选择本身是合理的。

**当前是怎么做的**
```
源路线 CSV
   ↓ manual_route_anchor.py  整体平移旋转到狗身上
route_runtime.csv
   ↓ build_horizontal_route.py  再按 ③ 的扶正旋转转一遍
route_horizontal.csv     ← 跟线器实际读这份
```
实测那次:1277 个路点整体搬运,旋转了 -15.67°。

**问题**

🔧 **结构**:三个脚本(对齐、扶正路线、起点检查)散在 `scripts/` 里,和别的脚本混着。

🎯 **设计 ★ 这是全系统最严重的一处(本轮不改)**:

**狗摆歪 1 度,没有任何环节能发现。** 推导:

```
你把狗放下,比录制时歪了 1 度
   ↓
对齐程序说:"好,狗朝这个方向,那我把整条路线也转 1 度对上它"
   ↓
路线和狗完美对齐了 —— 但整条路线相对真实地面,歪了 1 度
   ↓
狗沿着这条已经歪了的路线走,跟得极准(实测 3 厘米)
   ↓
所有检查、所有报告都说"优秀"
   ↓
真相:狗整条路都在错误的位置上,而且越走越偏
```

系统里**确实有**一道起点检查(`check_route_start_alignment.py`,不合格就中止巡检),
但它挡不住 —— **因为它跑在对齐之后**:

```
saas :2772   先跑对齐 → 产出 route_runtime.csv
saas :2777   再检查   → 检查的正是刚被转过来迁就狗的那份
```
两处指向同一个文件(已用真实数据实证:那次量到的差距是 **3.8 厘米**)。

**它量的是"对齐程序干活干成了没有",不是"狗摆得正不正"。结构上只可能通过。**

1 度的代价:@50m = 0.87m,@100m = 1.75m,**@436m = 7.61m**。

**本轮改成什么**
三个脚本搬到 `runtime/localization/`,内容不改。

**这个设计问题不在本轮范围** —— 它正是你第 2 步"狗要能自己定位、起点朝向要能自动矫正"的根因。
**要解决它需要一个真正的位置参照物**(地图配准或路标),那是新设计,不是搬代码能办的。

## ⑤⑥ 控制:算法和它的外壳

**现在有什么**
两个文件:**331 行的算法**,和**包着它的 1259 行外壳**。实际启动的是外壳。

**它在影响什么**
**这是唯一决定"狗往哪走、走多快"的地方。**

**通过什么方式**
每 50 毫秒跑一遍,四步:
1. 我在路线的第几个点?(只在上次位置前后 6 个点里找,而且一拍最多前进 1 格)
2. 从那里沿路线往前数 0.6 米,是哪个点?(**沿路线累加弧长,不是画圆求交**)
3. 那个点偏我多少度?→ 偏差 × 0.9 = 转速,上限 0.45
4. 偏得太多就别走:>57° 原地转,>29° 减半速,否则正常

**外壳干两件事:**
- **门禁**:等一个空文件出现、等数据够新鲜、等扶正锁好,全满足才放行调用算法;不放行就发零
- **记录**:每一拍写一条 40 多字段的 JSON(**你电脑端分析看的就是这个**)

**为什么需要外壳**
门禁是必须的 —— 前 56 个启动步骤做完狗还站着不动,**最后那个空文件出现才走**。
没有它,半启动状态下狗就会动。

**当前是怎么做的**
```
331 行算法    在 src/go2_fastlio_patrol/    是 ROS 包,用 ros2 run 启动
1259 行外壳   在 scripts/                    是裸脚本,用 python3 跑
                                             而且它继承那 331 行
```

**问题**

🔧 **结构一 ★ 本轮重点**:**发动机在车库,车壳在阁楼,车壳还是从发动机派生的。**
想看懂控制逻辑要同时开两个目录的文件,而且它们启动机制不一样。

🔧 **结构二 ★ 本轮重点**:**"决定往哪走"和"把决定记下来"写在同一段代码里**
(外壳 `control_loop` 共 310 行,其中 133 行在写记录)。

这条的后果最实际:**控制逻辑因此不是一个"给输入→给输出"的纯函数,
所以没法用历史数据回放验证** —— 而回放正是这次改造最需要的安全网。

还有一个 `reach_distance` 参数,传进去了、接收了,但全文只用于打印日志,**从不参与计算**。

## ⑦ 安全层

**现在有什么**
一个程序,夹在算法和狗腿之间。算法算出的速度**不直接给狗**,先过它。

**它在影响什么**
**它是唯一能否决算法的地方。**

**通过什么方式**
在狗身前划一个长方体盒子,数落在盒子里的雷达点:
```
前后 0.35~1.20 米   左右各 0.45 米   离地 0.25~0.90 米
盒子里 ≥12 个点 → 停
1 帧看到就停,连续 5 帧干净才恢复
```
再加一道限速(前进 ≤0.5、横移 ≤0.15、转速 ≤0.45)和两个失联保护
(算法 0.5 秒不说话 → 发零;雷达 1 秒没数据 → 发零)。

**为什么这几个数是这样**
- 离地 0.25 米起 —— **避开地面**,不然地面本身无数个点,永远在"停"
- 到 0.90 米止 —— **避开横梁**,狗从下面能过去
- 停用 1 帧、恢复要 5 帧 —— **不对称是故意的**:误停一下没事,误走一下可能撞人

**当前是怎么做的**
`unitree_safe_cmd_node.py`(569 行)+ `patrol_control.py`(471 行,前者从它引入三个函数)。

**问题**

🔧 **结构**:`patrol_control.py` 名字像"控制模块",没有任何启动脚本直接启动它,
**看起来像死代码** —— 我曾差点把它归档删掉,那会直接把狗弄瘫。
它实际是安全层的核心依赖。**位置和命名都误导。**

🎯 **设计(本轮不改)**:**"停"是纯二值的 —— 要么全速,要么零。没有减速,没有绕行。**
你要的"保持 50-70cm 平滑绕行",现在这层完全做不到。

**本轮改成什么**
两个文件一起搬到 `runtime/safety/`,放在一起,依赖关系就明显了。
**内容不改。**

**这里是将来 MID360 避障的位置** —— 你说了自己写、规则自己定,
搬完之后它有明确的地方放,不用再挤。

## ⑨ 编排:57 步

**现在有什么**
一个 **1250 行的函数**,负责按顺序把上面那些东西全部拉起来。

**它在影响什么**
**它决定巡检能不能起来。** 任何一步失败,整体回滚。

**通过什么方式**
57 条命令,每条带一个探针确认成功了才做下一步:
```
建目录 → 存证据哈希 → 起 UDP 收发 → 起安全层 → 起跟线器
  → 等 FAST-LIO 出新数据(失败退出码 44)
  → 路线对齐(失败退出码 47)
  → 起点检查 → 起看门狗 → 起录制
  → 等日志里出现 "FOLLOWER_HORIZONTAL_FRAME_READY"
  → 最后 touch 那个空文件 .motion_enabled     ← 总闸
```

**为什么要这么复杂**
因为顺序错了会出事:雷达没出数就起定位,定位会崩;
定位没稳就起跟线器,跟线器会拿到垃圾位置然后让狗乱走。

**当前是怎么做的**
```
start_patrol_command()  1250 行
  ├─ 912 行  算出 148 个局部变量(路径、参数、日志位置…)
  └─ 337 行  把这些变量拼成 57 条 shell 命令字符串
```

**问题**

🔧 **结构 ★ 这是全系统最严重的一处**:
**整个巡检的配置,在一个函数里算成 148 个局部变量,再拼成字符串。**

三个后果:
1. **没法测**。想知道"这次巡检会用什么参数",唯一办法是真跑一次
2. **看不出依赖**。148 个变量同一个作用域,谁依赖谁看不出来
3. **bug 藏得住**。⑤⑥ 那个"云端参数算了不用"就藏在这 912 行里 ——
   因为"算出来的变量"和"实际用的字面量"之间没有任何检查

**本轮改成什么**
```
现在:  1250 行函数 → 148 个局部变量 → 拼字符串
改后:  可测的配置构建 → 明确的配置对象 → 拼出同样的字符串
```
**验证标准:57 条命令串规范化后逐字节相同。差一个空格都算失败。**

**顺带**:那个"参数算了不用"会在配置对象里**当场暴露** ——
因为会明确出现"这个值算了但没被任何命令用到"。
**⚠️ 暴露 ≠ 修复。发现了先记下来,本轮不改。**

**它在影响什么**

**通过什么方式**

其余全是单点:位置来源只有 FAST-LIO;路线对齐只有一种;朝向锁完就冻。
**"停"这件事做了双保险,"走对"这件事一层保险都没有。**

**本轮改成什么**
