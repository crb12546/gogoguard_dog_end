# ⓪ 线的起点不是巡检,是五条常驻循环

## 白话

狗一开机,有**四个**程序自动跑起来,**一直跑到关机**。它们互相不知道对方存在,各干各的。

**巡检不在这四个里面。** 巡检是其中一个程序(命令循环)从云端收到一条"开始巡检"之后,
**临时**拉起来的第五摊东西,跑完就拆掉。

这一点很重要:**你在平台上点"开始巡检",不是启动了一个常驻服务,是触发了一次性任务。**

**而且雷达和定位也不是开机自启的** —— 它们同样是收到巡检命令后才被拉起来的。
狗开机后静止不动的时候,**雷达是不转的、FAST-LIO 是没在跑的**。

## 证据

Linux 上管开机自启的机制叫 systemd,每个自启项是一个 `.service` 文件。
**狗上实际 enable 且 running 的团队服务有 4 个**(2026-08-01 真机核验):

| 文件 | 开机拉起什么 | 干什么 |
|---|---|---|
| `systemd/go2-saas-command.service` | `go2_saas_agent.py command-loop --interval 5` | **每 5 秒问云端一次:有活吗?** |
| `systemd/go2-saas-video.service` | `video-loop --seconds 20 --upload` | 视频分段录制 |
| `systemd/go2-saas-outbox.service` | `outbox-loop --interval 10` | 网断了攒着的文件,通了补传 |
| `systemd/go2-wired-ssh-rescue.service` | `go2_wired_ssh_rescue.sh` | 有线网口保底登录(4G 挂了还能连上狗) |

## ⚠️ 更正(2026-08-01 真机核验)

本文早先版本写"五条常驻循环",把 `deploy/systemd_user/go2-fastlio-base.service`
(雷达+定位底座)算作第五条。**这是错的。**

真机核验:
```
systemctl --user status go2-fastlio-base  →  Unit could not be found
~/.config/systemd/user/                    →  无 go2 单元
```

它**只是仓库里的一个文件,从来没安装到狗上、没有 enable**。

**真相**:雷达 + FAST-LIO 底座是巡检启动链里由 `base_bringup.sh` 按需拉起的。
开机 3 分钟时的进程表核实:**一个 FAST-LIO、一个雷达进程都没有**,只有上表 4 个。

**这处错误说明了一件事**:仓库里存在一个 `.service` 文件,
**不等于**它在狗上生效。判断自启必须看 `systemctl list-unit-files --state=enabled`,
不能看仓库里有什么文件。

## 为什么是这个设计

因为**巡检可能失败**。如果巡检是常驻服务,它崩了整个狗就失联了。
现在的做法是:**通信和救援是常驻的,干活是临时的**。干活那摊崩了,通信还在,你还能在平台上看到、还能 SSH 上去。

# ① 录制:路线怎么变成一个文件

## 白话

狗不知道路线在哪。所以**第一步必须有人拿手柄带着它走一遍**,走的过程中狗把自己走过的位置记下来。

记的方式是:**每往前走 0.4 米,就记一行**。记的内容是"我在哪(x, y)、我朝哪(yaw)、该多快(v)"。

一条 436 米的路线,大概记 1100 行。这个文件就是路线。

## 代码

文件:`src/go2_fastlio_patrol/go2_fastlio_patrol/route_recorder.py`

```python
:23   declare_parameter('min_distance', 0.4)      # 设定:每 0.4 米记一次
:90   if dist >= self.min_distance:               # 判断:离上次记录点够远了吗
:94       self.writer.writerow([id, x, y, yaw, v]) # 动作:记一行
```

## 逐行讲

- **`:23`** —— 定义一个叫 `min_distance` 的设定值,默认 0.4(米)。
- **`:90`** —— 每收到一次自己的位置,算一下"离上次记的那个点有多远",如果 ≥ 0.4 米就记,否则跳过。
- **`:94`** —— 记一行,5 个数:
  - `id` 第几个点(0, 1, 2, 3…)
  - `x` `y` 位置坐标(米)
  - `yaw` 朝向角度(弧度)
  - `v` 速度

## 为什么是 0.4 米

太密(比如 0.05 米)→ 文件巨大,而且记录噪声会被完整保留,路线变得抖;
太疏(比如 2 米)→ 拐弯处的形状丢了,狗会切角。

0.4 米是个折中。**这个数没有理论依据,是调出来的。**

## ⚠️ 这里有个坑:`v` 是假的

那个速度值 `v`,**不是狗当时实际走多快**,是一个写死的常数:

```python
:24   declare_parameter('default_speed', 0.20)   # 不管实际多快,一律记 0.20
```

所以路线文件里每一行的 `v` 都是 `0.20`,完全一样。

**后果**:后面走这条路线的时候,程序**根本不读这个 `v`** —— 读了也没用,全是一样的数。
速度是从云端另外传的。

**这是第一个"代码写了但没意义"的地方。**

## 分支①从这里岔开

录制和巡检**不能同时干**。靠一个空文件 `.route_recording_enabled` 互斥:
这个文件存在 = 正在录制 = 巡检不许启动。

# ② 定位:狗怎么知道自己在哪

## 白话

上一节说"记下自己的位置"—— 但位置从哪来?

- GPS?室内没信号,而且精度 3-5 米,巡检要的是厘米级。
- 轮式里程计(数轮子转了几圈)?四足狗没有轮子。

所以用**激光雷达 + SLAM**。

雷达每秒往四周打十万个激光点,测出"周围的墙、柱子、地面分别离我多远"。
把这一帧的形状,和上一帧的形状对齐,就能算出"这 0.1 秒我往前挪了多少、转了多少"。
一路累加,就知道自己在哪了。

跑这个算法的程序叫 **FAST-LIO**。

## 证据

```
Livox MID-360 雷达 → src/FAST_LIO/src/laserMapping.cpp → 发出位置信息
```

## ⚠️ 这里有个结构性事实

**这是全系统唯一的位置来源。没有第二个位置源做交叉验证。**

意思是:如果 FAST-LIO 算错了,**没有任何东西能发现**。狗会坚信自己在一个错误的地方,
然后按照那个错误的位置去走路线。

（配套有两个探针:`check_livox_stream.py` 查"雷达有没有出数",
`check_fastlio_freshness.py` 查"位置是不是新的"。但它们只能查"有没有数",查不了"数对不对"。）

# ③ 扶正:为什么必须有这一步

## 白话 —— 这一节是全系统最反直觉的地方,值得慢慢看

雷达是**斜着装在狗背上的**,往下倾斜大约 **34 度**(实测 34.324°)。

问题在于:FAST-LIO 不知道雷达是斜的。它默认"雷达的正上方 = 世界的正上方"。

于是它算出来的整个世界,是**歪着 34 度的**。

**具体会怎样?** 打个比方:

> 你戴着一副歪 34 度的眼镜看房间。你会觉得地板是斜的、墙是斜的。
> 你在这个歪的视角下画一张房间地图 —— 地图本身是"自洽"的,你按图走也能走通。
> **但地图上的"高度"和真实的"高度"对不上了**:真实平地上走 10 米,
> 在你的歪地图上会显示"同时上升了 5.6 米"。

对巡检的实际影响:

1. 记路线时是在歪的系里记的,走路线时也在歪的系里走 —— 只要两次一致,**居然能走通**。
2. 但只要中间有任何一次"系"变了(比如定位重启),两边就对不上,狗会走飞。
3. 而且高度信息完全没法用(比如判断"前面是台阶还是墙")。

**所以必须先把世界扶正。**

## 怎么扶正?用重力

重力永远指向真正的"下"。所以只要测出"重力在雷达坐标系里指哪个方向",
就知道雷达歪了多少,反着转回来就正了。

测重力用 **IMU**(惯性测量单元,手机里也有,就是那个测你手机横竖屏的东西)。

## ⚠️ 但雷达自己的 IMU 也是歪的

雷达的 IMU 和雷达装在一起,雷达歪它也歪。它报的"重力方向"当然也是歪的。

**所以需要第二个 IMU 做对照 —— 这就是狗身上那个 IMU 存在的全部理由。**

- 雷达 IMU 装在雷达上(歪的)
- 狗身 IMU 装在狗身上(正的)

两个各自测一次重力,**互相对答案**。如果两个说的差太多,说明至少有一个在瞎报,这次测量作废。

## 代码

文件:`scripts/waypoint_follower_go2_2_trace.py`

```python
:214  horizontal_frame_samples = 15                       # 要攒够 15 次一致的测量
:223  horizontal_frame_max_source_disagreement_deg = 3.0  # 两个 IMU 差超过 3 度就作废
:318  q_lidar_gravity_correction_xyzw                     # 标定文件里预存的挂载修正
```

两个 IMU 各自的数据入口:
```python
:546  def lidar_imu_callback(self, message)   # 雷达 IMU 的数据从这进来
:515  def body_yaw_callback(self, message)    # 狗身 IMU 的数据从这进来
```

## 逐行讲

- **`:223` 的 3.0 度** —— 两个 IMU 报的重力方向,夹角超过 3 度就丢弃这次测量。
  为什么是 3 度?IMU 本身有噪声,完全一致不可能;3 度是"噪声容得下、真错误容不下"的分界。
- **`:214` 的 15 次** —— 不是测一次就信,要连续攒够 15 次都一致才敢用。
  为什么?狗在启动瞬间可能在晃、可能有人在碰它,单次测量不可靠。
- **`:318`** —— 除了实时测的,还有一份出厂/上次标定存下来的修正量,作为参考基准。

## 锁完就冻死,整趟不再改

算出那个"扶正旋转"之后,**立刻冻结,整趟巡检不再更新**。

**为什么不持续更新?** 因为路线是在某一个坐标系里记的。
坐标系一变,路线上所有的点的含义就都变了 —— 相当于走到一半突然换了张地图。

**代价**:如果启动那一刻测错了,整趟都错,而且没有机会纠正。

# ④ 路线对齐:把路线转到狗身上

## 白话

录路线的时候,狗站在 A 点朝北。
今天要跑这条路线,你把狗放在 A 点附近 —— 但不可能完全一样,总会差个几十厘米、几度。

**怎么办?两个思路:**

- **思路一**:把狗挪到和录制时完全一样的位置。→ 做不到,人手放不准。
- **思路二**:**把路线整体平移+旋转,让路线的起点正好落在狗现在的位置上。** ← 现在用的

思路二就是"路线对齐"。整条路线像一张纸,整体挪一挪、转一转,让起点对上狗。

## 代码 —— 这里是个二选一

文件:`scripts/go2_saas_agent.py`

```python
:2319  if   relocalization["manualAnchor"]:        → manual_route_anchor.py   ← 默认走这条
       elif relocalization["pcdRelocalization"]:   → route_relocalizer (C++)  ← 默认不走
```

默认是第一条(`:3581` 写着 `default="manual_anchor"`)。

**两条的区别:**

| | manual_anchor(在用) | PCD 重定位(备用) |
|---|---|---|
| 怎么定起点 | **假设狗现在就在起点** | 拿实时点云和地图做配准,**算出**狗在哪 |
| 需要什么 | 什么都不需要 | 需要一张预先建好的点云地图 |
| 人要做什么 | **把狗尽量放准** | 放个大概就行 |
| 代码状态 | 在跑 | 写好了、编译进去了、57 步里有位置,**就是没被选中** |

## 产出链

## ⚠️⚠️ 这里是全系统最要命的地方,单独讲

### 问题:狗摆歪 1 度,谁能发现?

**答案:没有人能发现。** 而且这不是疏忽,是结构决定的。

推导一遍:

```
第 1 步  你把狗放下,比录制时歪了 1 度。
           ↓
第 2 步  manual_anchor 说:"好,狗朝这个方向,那我把整条路线也转 1 度,对上它。"
           ↓
第 3 步  现在路线和狗完美对齐了 —— 但整条路线相对真实地面,歪了 1 度。
           ↓
第 4 步  狗沿着这条(已经歪了的)路线走,跟得极准 —— 实测偏差 0.0295 米(不到 3 厘米)。
           ↓
第 5 步  所有的检查、所有的报告都说:"跟线误差 3 厘米,优秀。"
           ↓
真相     狗其实整条路都在错误的位置上,而且越走越偏。
```

**1 度到底差多少?**

| 走了多远 | 偏离真实路线 |
|---|---|
| 50 米 | 0.87 米 |
| 100 米 | 1.75 米 |
| 436 米(实际路线长度) | **7.61 米** |

7.61 米 —— 巡检点全部错位,该拍的东西拍不到,可能直接撞墙。

### 那道"起点对齐检查"为什么挡不住

系统里**确实有**一个专门检查起点的程序:`check_route_start_alignment.py`(204 行)。
它会在不合格时**中止整个巡检**:

```python
:195  if distance > max_distance or abs(yaw_error) > max_yaw_error:
:196      print("ROUTE_START_NOT_ALIGNED ...")   → 退出 → 整个巡检回滚
```

**白话**:如果"狗的位置"和"路线起点"差太多,或者朝向差太多,就报错停止。

看起来正好能挡住 1 度问题。**但它挡不住,原因在执行顺序。**

```
go2_saas_agent.py 的执行顺序:

:2772   先跑 manual_anchor   →  把路线转到狗身上
              ↓
        产出 route_runtime.csv     （:2326 的 --output-route 就是它)
              ↓
:2777   再跑 check_route_start_alignment --route-file route_runtime.csv
              ↑
        它检查的,正是刚刚被转过来迁就狗的那份路线
```

关键证据:`:1956` 定义 `route_arg = route_runtime.csv`,
而 `:2326` 里 manual_anchor 的输出参数 `--output-route` 用的也是 `route_arg`。
**同一个文件。**

**所以这个检查在量什么?**

它量的是:**"manual_anchor 这个程序干活干成了没有"**。
它量的**不是**:"狗摆得正不正"。

路线已经被转到迁就狗了,再去比"狗和路线起点差多少" —— 当然几乎为 0。
**这道闸在结构上只可能通过。**

这不是"概率上很少触发",是**代码顺序上的死结**。

### 这就是你要的第 2 步新功能的根因

你说"狗要能自己定位、起点朝向要能自动矫正" —— 根因就在这里:
**现在的系统没有"真实世界"这个参照物,它只跟自己比。**

# ⑤ 跟线器:真正的算法,331 行

## 白话

有了路线(一串点),有了自己的位置,现在要决定:**这一瞬间,该往哪走、走多快?**

用的方法叫"纯追踪"(pure pursuit),日常类比是:

> 你开车不会盯着车头前 10 厘米看,你会看**前面几十米的路**,朝那个方向打方向盘。
> 车往前开,你的注视点也往前移。

程序做的是一样的事,四步:

1. **我现在在路线的哪一段?**
2. **从那里往前数 0.6 米,是哪个点?** ← 这就是"注视点"
3. **那个点在我的左前方还是右前方?偏多少度?** → 决定转多快
4. **偏得太多就先别走,原地转;偏得不多就正常走。** → 决定速度

**整个算法就这四步,加一个"卡住了怎么办"的兜底。没有 PID,没有轨迹规划,没有预测。**

文件:`src/go2_fastlio_patrol/go2_fastlio_patrol/waypoint_follower_go2_2.py`,
每 **50 毫秒**(一秒 20 次)跑一遍(`:98`)。

---

## 第一步:我在路线的哪一段

### 白话

路线是 1100 个点。要知道"我现在离哪个点最近"。

**笨办法**:1100 个点全算一遍距离,取最小。—— 慢,而且有个致命问题:
如果路线是个回环,或者两段路挨得近,可能算出"最近的是第 900 个点",
而实际上你才走到第 100 个点。**狗会突然掉头往回走。**

**实际做法**:只在"上次的位置前后各 6 个点"里找。走到第 100 个点,就只看第 94~106 个点。

### 代码

```python
:153  def find_nearest_window(self):
:156      start = max(0, self.nearest_index - 6)      # 往前看 6 个
:157      end   = min(n-1, self.nearest_index + 6)    # 往后看 6 个
          # 只在这 13 个点里找最近的
```

### 逐行讲

- `nearest_index` = "我上次算出来在第几个点"
- `start` / `end` = 搜索范围,上次那个点 ±6
- `max(0, ...)` 和 `min(n-1, ...)` 是防越界:路线开头别搜到负数,结尾别搜出界

### 还有一道保险:只许前进,不许倒退

```python
:177   self.nearest_index = min(new_i, self.nearest_index + 1)
```

**白话**:就算这次算出来"最近的是第 105 个点",也**最多只允许推进到第 101 个**。
一拍最多前进 1 格。

**为什么**:防止定位抖一下导致索引跳跃。索引跳了,注视点就跳了,狗会猛打方向。

### 万一真的偏离很远了呢

```python
:183   if new_d > self.relocalize_distance:    # 运行时 = 1.5 米
           # 允许全局重搜一次
```

**白话**:如果发现"最近的点也在 1.5 米之外",说明真的偏离路线了,
这时候才允许放弃"只看附近"的规矩,回到笨办法全局搜一遍。

## 第二步:找前面 0.6 米那个点

### 白话 —— 这是你上次问的那个

**不是**画个半径 0.6 米的圆,看它和路线交在哪。
**是**从当前位置开始,**沿着路线一段一段往前加距离**,加够 0.6 米就停。

### 代码

```python
:195  def compute_lookahead_index(self):
:198      acc = 0.0                                    # 累计走过的距离
:200      while True:
:208          seg = hypot(p1.x - p0.x, p1.y - p0.y)    # 这一小段有多长
:209          acc += seg                               # 加进总数
:212          if acc >= self.lookahead_distance:       # 够 0.6 米了吗
:213              return i                             # 够了,就是这个点
```

### 逐行讲

- `hypot(dx, dy)` = 勾股定理,算两点直线距离 √(dx² + dy²)
- `acc` 从 0 开始,一段一段往上加
- 加到 ≥ 0.6 就返回当前点的编号

### 这两种做法有什么区别

**在直路上没区别。在弯道上区别很大:**

```
直路:  当前 ●————————————● 0.6米外    沿路 0.6 米 = 直线 0.6 米
                                       两种做法一样

弯道:  当前 ●
              ╲                        沿路走 0.6 米
               ╲                       但直线距离只有 0.45 米
                ●  ← 0.6米(沿路)      → 注视点比想象中"近"
                                       → 转得更急
```

**后果**:弯道上会自动转得更急一点。**这是好事**(弯道本来就该转急),
但它是这个实现方式**顺带**产生的,不是有意设计的。

## 第三步:算转多快

### 白话

知道注视点在哪了,现在算:那个点在我的左边还是右边?偏多少度?
偏得越多,转得越快。

### 代码

```python
:277  alpha    = normalize_angle(atan2(dy, dx) - self.current_yaw)
:279  yaw_rate = self.k_yaw * alpha
:280  yaw_rate = max(-self.max_yaw_rate, min(self.max_yaw_rate, yaw_rate))
```

### 逐行讲

- **`atan2(dy, dx)`** —— 目标点相对我在哪个方向(绝对角度)
- **`- self.current_yaw`** —— 减掉我现在的朝向,得到"相对我偏了多少"。这个差值叫 `alpha`
- **`normalize_angle`** —— 把角度收进 −180°~+180°。
  否则会出现"要转 350 度"这种荒谬结果(实际应该是往反方向转 10 度)
- **`k_yaw * alpha`** —— 偏差 × 一个系数 = 转速。这是最简单的比例控制
- **`max(..., min(...))`** —— 夹在上下限之间,不许超过 `max_yaw_rate`

### 数字的含义

运行时 `k_yaw = 0.900`,`max_yaw_rate = 0.450`(弧度/秒)。

- 偏 10 度(0.175 弧度)→ 转速 0.157 弧度/秒 ≈ 9 度/秒
- 偏 30 度(0.524 弧度)→ 转速 0.471 → **超上限,砍到 0.450** ≈ 26 度/秒

也就是说:**偏差超过约 28.6 度以后,转速就顶格了,再偏也不会更快。**

## 第四步:分三档定速度

### 白话

如果目标在我正前方,大胆往前走。
如果目标在我侧面 40 度,边走边转会走出一个大弧,偏得更远 → 减速。

速度:      全速      半速        0(原地转)

# ⑩ 云端:为什么只能狗主动

## 白话

狗背着 4G 上网卡。**4G 没有固定公网 IP** —— 运营商每次分配的地址都不一样,
而且在运营商的 NAT 后面。

**结果**:平台**连不进来**。

所以只能反过来:**狗每 5 秒主动打一次电话给平台**。

一次 POST 请求:
- **请求体带上去**:狗的状态(位置、电量、在不在巡检、各进程死活)
- **响应体带下来**:平台有没有新命令(开始巡检/停止/录制…)

**一个接口,两个方向。** 这就是为什么"上报"和"接收命令"在代码里是同一个函数。

## 代码

# ⑪ 观测:你在电脑上分析的数据从哪来

**这套设计是对的。问题是它的代码量(5370 行)比它观测的对象(3125 行)还大 72%。**

# ⑫ 监督:两条独立的看门狗

## 第一条:定位会话守卫

文件:`scripts/localization_session_guard.py`(241 行),巡检期间临时起,巡检结束就没了。

### 白话

它盯着一件事:**FAST-LIO 有没有重启过**。

判断方法很直接:**记下开始时 FAST-LIO 的进程编号(pid),之后一直对比。pid 变了 = 它重启过了。**

```python
:185  expected.get("pid")             # 开始时记下的 pid
:232  abort_operation(args, reason)   # pid 变了 → 中止
```

### 为什么 FAST-LIO 重启是致命的

因为 FAST-LIO 一重启,**它的坐标原点就重置到"现在这里"了**。

而路线是按照重启前那个原点对齐的。原点变了,整条路线的坐标全部作废。
**此时继续走,狗会按照一套错误的坐标去走,大概率撞。**

### 它怎么处理

```bash
:73-77  pkill 掉:跟线器、安全层、两个 UDP 搬运工、观测进程、rosbag
        并往 manifest 写:abort_reason=localization_session_changed
```

**宁可停,不冒险。** 而且留下记录说明为什么停的。

## 第二条:底座健康看门狗

文件:`scripts/go2_base_health_watchdog.py`,**常驻**(不随巡检退出)。

`go2_saas_agent.py:2788` 起 —— 注意写法是"**如果还没在跑就起一个**",
所以它跨巡检存活。触发时同样调 `motion_probe stop`。

## ⚠️ 这是全系统唯一有冗余的地方

- **两条看门狗**:一条盯定位会话,一条盯底座健康
- **两把刹车**:ROS 链发零 + `motion_probe` 绕过 ROS 直连 SDK

**其余全是单点:**

| | 有几个 |
|---|---|
| 位置来源 | 1 个(FAST-LIO) |
| 路线对齐方式 | 1 种(manual_anchor,PCD 那套没启用) |
| 朝向基准 | 1 个(启动时锁死,之后不再更新) |

**"停"这件事被做了双保险,"走对"这件事一层保险都没有。**

# ⑬ 证据链

## 白话

停止时,`go2_experiment_snapshot.py` 把关键文件算个哈希值存档。

哈希 = 文件内容的指纹。内容改一个字节,指纹就完全变了。

**为什么要这个**:一个月后你看某次巡检结果不对,想知道"当时用的到底是哪版路线、哪版代码"。
文件名可能重名、可能被覆盖,**哈希不会骗人**。

路线的匹配也是**认哈希不认文件名**(带内容别名回退)。
