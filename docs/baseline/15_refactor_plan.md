# 一、这次改造的底线(先说死,后面所有决定都受它约束)

你说过:**"结果是一样的,狗走的还是那么准,还能跟 saas 平台对接上。"**

这句话把这次改造定死成 **"只搬东西,不改行为"**。具体是这五条:

| 不能动 | 动了会怎样 |
|---|---|
| 跟线算法的四步逻辑 | 狗走的路线就变了 |

最后一条特别重要 —— 你说过"我电脑端会去做数据分析,看走的准不准"。
那些输出文件是**你和代码之间的合同**,不能单方面改。

# 二、当前的问题(每条都有证据,不是感觉)

## 问题 1 · 一个 1250 行的函数掌管整个巡检启动 ★最严重

`go2_saas_agent.py` 里的 `start_patrol_command()`,第 1683 行到 2932 行:

```
1250 行
  ├─ 912 行  变量准备      ← 148 个局部变量
  └─ 337 行  命令列表      ← 把那 148 个变量拼进 57 条 shell 命令串
```

**白话**:整个巡检要用的所有配置 —— 走多快、路线在哪、日志写哪、每个进程怎么启动 ——
全都在**一个函数里算成 148 个变量**,然后拼成字符串丢给 shell 执行。

**后果三条:**
1. **没法测**。想知道"这次巡检会用什么参数",唯一办法是真跑一次巡检。
2. **看不出依赖**。148 个变量在同一个作用域里,谁依赖谁看不出来。
3. **bug 藏得住**。下面问题 2 那个 bug 就藏在这 912 行里,藏了很久。

## 问题 2 · 云端参数算了一大堆,只有两个真的送到了控制器

代码在 `:1685–1790` 从云端读参数、做边界检查、算出结果:
```
k_yaw                        默认 1.20
tracking_lookahead_distance  默认 0.50
max_yaw_rate                 默认 0.60
min_track_yaw_rate           默认 0.20
...
```

但真正启动跟线器的那行命令(`:2482`)是**写死的**:
```
-p k_yaw:=0.900   -p max_yaw_rate:=0.450   -p lookahead_distance:=0.600
-p search_window:=6   -p turn_in_place_angle:=1.000   -p slow_down_angle:=0.500
```

**云端只有速度和往返模式两个参数真的到了控制器,其余全部算完就扔。**

**白话**:你在平台上调这些参数,狗上不会有任何变化。

**为什么这个 bug 能活这么久**:因为配置是字符串拼接,
"算出来的变量"和"实际用的字面量"之间没有任何检查。

## 问题 3 · 算法和包着它的外壳,住在两个地方,启动方式还不一样

```
331 行的算法      src/go2_fastlio_patrol/...  是 ROS 包,用 ros2 run 启动
1259 行的外壳     scripts/                     是裸脚本,用 python3 直接跑
                                               而且它继承那 331 行
```

**白话**:发动机在车库,车壳在阁楼,而且车壳是从发动机"派生"出来的。
想看懂控制逻辑要同时开两个目录的文件,而且它们的启动机制不一样。

## 问题 4 · 记录数据的代码,长在决策逻辑里面

外壳的 `control_loop`(:889–1199)一共 310 行,其中 **:1065–1197 共 133 行是在写记录文件**。

**白话**:"决定往哪走"和"把这次决定记下来"这两件事,写在同一段代码里,分不开。

**后果**:控制逻辑不是一个"给它输入就给你输出"的纯函数,
所以**没法用历史数据回放验证** —— 而回放正是这次改造最需要的安全网。

## 问题 5 · 进程之间靠 6 类约定通信,其中 5 类没有任何校验 ★最危险

这个系统的进程之间**不通过函数调用**,全靠约定:

| 类型 | 数量 | 举例 | 改错会怎样 |
|---|---:|---|---|
| 门文件 | 7 | `.motion_enabled` 存在=允许动 | 改名 → 狗永远不动,不报错 |
| 日志字符串当信号 | 5 | 等日志里出现 `FOLLOWER_HORIZONTAL_FRAME_READY` | 改文案 → 启动永远卡住 |
| 退出码 | 11 | `exit 44` = FAST-LIO 不新鲜 | 改数字 → 错误被当成别的错误 |
| 环境变量 | **174** | `GO2_SDK_IF` | 改名 → 默默用默认值 |
| ROS 话题 | 5 | `/patrol_cmd` | 改名 → 指令发不到,不报错 |
| `/dev/shm` 共享文件 | 1 生产者 / **5 消费者** | `go2_fastlio_latest_odom.txt` | 路径变 → 5 个地方同时瞎 |

**白话**:这 6 类里有 5 类是"约好的字符串"。**改错一个字母,程序照样启动、照样不报错,
只是某个环节永远等不到它要的信号。**

这是这次改造**最大的风险源**,也是必须先建验证网的原因。

## 问题 6 · 观测层比它观测的对象还大 72%

```
让狗动的全部代码    3,125 行
记录和观测的代码    5,370 行
```

**不是说观测没用** —— 你就是靠它做分析的。是**位置不对**:它长在被观测的东西里面。

## 问题 7 · 离线建图 4,228 行和巡检运行时混在同一个 `src/`

`go2_loop_backend/` 18 个文件,**巡检期间一个都不跑**,是事后在电脑上手动跑的。
但它和巡检代码放在同一个 `src/` 下,`colcon build` 每次都编它。

# 三、为什么会长成这样(根因,不是骂人)

**这不是能力问题,是演进路径决定的。**

```
系统一开始要"能跑起来"
      ↓
每加一个需求 → 在 saas 里再加一段(因为那里最方便)
      ↓
没有测试 → 不敢动已有的代码 → 只能继续追加
      ↓
进程间用字符串约定 → 加东西不用改接口,很方便
      ↓                    但也意味着没有任何约束
1250 行的函数 · 174 个环境变量 · 算了不用的参数
```

**关键一环是"没有测试 → 不敢重构 → 只能追加"。**
所以这次改造的第一件事不是搬代码,**是先把测试网建起来**。

# 七、这次明确不做什么

| 不做 | 为什么 |
|---|---|
| 不改算法逻辑 | 违反底线 |
| 不改任何参数值 | 同上 |
| **不改门文件名 / 日志文案 / 退出码 / 话题名** | **最危险的一类**。要改也得等契约网建好之后,单独一轮 |
| 不修"云端参数算了不用" | 这是改行为。先暴露、先记录,单独决定 |
| **不合并进程** | 见下 |
| 不做避障 | 那是第 2 步的新需求,在本次改造之后 |

## 关于"要不要合并进程"

现在巡检要拉起十几个进程,其中几个(跟线器 + 安全层 + UDP 发送)完全可以是一个进程。
合并能直接降 CPU 和上下文切换。

**但这次不做,理由是顺序:**

现在代码散在各处,**你根本看不出该合并谁跟谁**。
归位做完之后,哪些东西天然属于同一个进程是一眼能看出来的,那时合并是个小步骤。

**现在就合并 = 一边找东西一边拆墙。**

# 八、我自己找的反例(证伪自己的方案)

按你说的"通过找反例去证明自己可能有问题",我逐条质疑了上面的方案:

## 反例 1:回放台会不会验了个假的?

**质疑**:trace 里记的 `cmd_vx` 是"已发布的指令",而算法算出来的值可能在发布前被改过。
如果中间还有一层加工,回放对上了也不能证明算法一致。

**核查**:外壳的 `capture_published_command`(:631)是挂在发布器上的钩子,
`RecordingPublisher.publish`(:140)在**真正发布的那一刻**抓取。所以 trace 里的就是实发值。
**反例不成立**,但**回放必须比对"实发值"而不是中间变量** —— 已写进方案。

## 反例 2:控制逻辑真的能变成纯函数吗?

**质疑**:算法是有状态的(`nearest_index` 跨周期累积、`last_progress_time` 计时)。
纯函数做不到。

**核查**:**这个质疑成立。** 算法确实有状态。
**方案修正**:回放要做两种 ——
- **逐周期**:喂入记录中的 `nearest.index` 当输入,只验单周期数学(能精确定位错在哪)
- **全程**:从第 0 周期开始自己滚状态,验整条轨迹(更强,但一处偏差会级联)

**两种都做**。已补进第 0 步。

## 反例 3:57 条命令串"一字不差"这个标准现实吗?

**质疑**:命令串里含运行目录名、PID 文件路径,每次都不一样,不可能一字不差。

**核查**:**这个质疑成立。** `next_patrol_run_dir()`(:1551–1569)生成的是
`xunjian-<日期>-<当天序号>`(实例:`xunjian-20260726-02`)——
不是完整时间戳,是**日期 + 当天递增序号**,所以每次仍然不同。
命令串里所有基于它的路径(日志、pgid、manifest、trace)也跟着变。

**方案修正**:比对前要把"每次必然不同的部分"规范化成占位符
(运行目录名 → `<RUN>`、日期 → `<DATE>`)再比。已写进第 0 步 0-b。

> 顺带:**反例 1 的证据已核实成立** ——
> `RecordingPublisher.publish`(:140-142)是先调 `capture_published_command(message)`
> **再**转给真正的发布器,抓的确实是实发的那个 Twist,不是中间变量。

## 反例 4:"先建测试网再改"会不会先卡在第 0 步?

**质疑**:如果 0-a 回放对不上,方案就停在起点了。

**核查**:**这个风险真实存在,而且是好事** ——
对不上说明我对系统的理解有偏差,那种情况下更不该动代码。
**方案态度**:0-a 对不上就停下来查清楚,不硬推。**这是特性不是缺陷。**

## 反例 5:改造过程中狗要用怎么办?

**质疑**:改造期间原目录被动过,狗就不能出工了。

**核查**:**这个必须解决。**
**方案约束**:全程在独立目录改,`/home/unitree/go2_fastlio_ws` **一个字节不动**,
直到第 6 步真机验证通过、你明确点头,才考虑切换。**切换要有一键回滚。**
(测试目录 `/home/unitree/go2_dog_clean_test` 已建好并保留,编译产物在。)

## 反例 6:只有一次巡检记录,够不够?

**质疑**:6833 条都来自同一次巡检、同一条路线、同一组参数。
换条路线、换个速度,回放可能盖不住。

**核查**:**这个质疑成立,是本方案最大的覆盖盲区。**
狗上有 `patrol_logs/runs/` 多天记录(20260723–20260726),
**第 0 步应尽量多收几次不同路线/参数的记录进回放台。**
已补进第 0 步。
⚠️ 但要诚实:**即使收全,也只覆盖"曾经跑过的情况"。** 所以第 6 步真机验证不可省。
